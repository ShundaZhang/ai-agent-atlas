01 / FIELD NOTES

A coding task with a real workspace

Use Codex to explore, edit, run checks and produce reviewable code changes.

Choose a surface by where the code and feedback live: the desktop app organizes projects and tasks, an IDE keeps nearby code visible, the CLI works from a repository, and cloud work uses a configured remote environment. Actual tools, network access and permissions depend on the surface and settings. Do not assume a task sees every file or uses the same environment as another task.

Before a first change, establish the repository, relevant paths, working-tree state and a fast verification method. Give Codex a concrete behavior change and constraints. Review the resulting diff and observed checks, not only the explanation.

02 / FIELD NOTES

Make repository context small and durable

AGENTS.md carries repository guidance; a skill carries a specialized workflow.

Codex discovers applicable instruction files according to its documented scope and precedence. Write durable facts: setup, architectural constraints, relevant checks and where generated files come from. Keep one-off requests out of global instructions. A nested directory can need its own guidance; inspect the current documentation when overrides matter.

# Example repository guidance
Generated HTML comes from build.py; edit the source notes.
Run python3 -B build.py after content changes.
Check local links and language pairs before completion.
Report the changed pages and any unverified behavior.

Keep skills short enough to discover and narrow enough to test. A “prepare release notes” skill should specify source inputs and reviewable output; it should not silently acquire publication credentials.

03 / FIELD NOTES

One change, one visible acceptance condition

Use a bounded patch task before a large autonomous refactor.

Fix the local invoice filter: tenant A must not see tenant B records.
Read the implementation and the existing fixtures.
Preserve the API and valid owner access.
Reproduce the failure, change the filter, and run the affected checks.
Finish with the diff, observed results, and remaining limitations.

For longer tasks, keep a concise plan and checkpoint in the workspace. Separate independent changes with branches or worktrees when needed. Use the permission policy appropriate to the task; sandbox access and authorization to publish are distinct. A stopped or interrupted run needs its current state checked before continuing.
