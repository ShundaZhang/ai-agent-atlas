01 / FIELD NOTES

Evaluate the job you actually need done

An evaluation harness turns acceptance criteria into repeatable observations.

Build representative cases with expected outcomes, evidence requirements and forbidden side effects. Include missing data, conflicting versions, malformed tool results, timeouts and unauthorized actions. Keep a held-out set that prompt tuning does not consume. Compare against a simple baseline, such as deterministic code or a single model response.

Unit tests assess a component. End-to-end evals assess the task outcome. Traces help locate where a run went wrong. Record the model/runtime version, prompt, dataset revision, tool configuration and environment. A benchmark score transfers only to the extent that its tasks and conditions resemble yours.

03 / FIELD NOTES

Use judges carefully and keep objective checks

An LLM judge can apply a rubric; it is another fallible component.

Use executable assertions for objective properties where possible. For open-ended answers, define a rubric, blind system labels and calibrate a judge against expert-reviewed cases. Test sensitivity to answer length, ordering and persuasive wording. A model agreeing with another model is not independent evidence of factual correctness.

Repeat stochastic runs and report uncertainty. Tune on development cases; then run the held-out comparison once the candidates are fixed. Keep qualitative failure examples next to aggregate scores. The local evaluation exercise uses made-up fixed results to teach the denominator and policy tradeoff.
