01 / FIELD NOTES

Make the requested result testable

A useful prompt is a task specification whose missing details have consequences.

Describe the goal, audience, authoritative inputs, desired output and material constraints. Add success criteria that can be checked outside the model. Give examples when format or domain conventions are ambiguous. Start concise; expand only where a failure or actual constraint justifies it.

Task: Compare the two supplied protocol drafts.
Output: a table of changed requirements, with section references.
Preserve: the distinction between normative text and commentary.
Completion: every change is supported by both drafts; label ambiguities.

02 / FIELD NOTES

Use an output contract and a separate validator

Valid JSON answers a syntax question, not every semantic question.

A schema can require fields, enum values and types. Your application still needs to check identifiers, source support, bounds and business rules. Handle refusals, incomplete outputs and API errors explicitly. If the task asks for a temperature from a report, a valid numeric field can still contain the wrong unit or a number invented by the model.

Few-shot examples should cover edge behavior: missing evidence, conflicting values and an allowed “unknown.” Evaluate new cases instead of repeatedly patching a prompt to memorize the same small set.

03 / FIELD NOTES

Diagnose the failing layer before rewriting the prompt

Many apparent prompting failures are data, retrieval, tool or validation failures.

ObservationInvestigate first
Correct answer is absent from the supplied materialMissing evidence, retrieval recall or task scope
Answer quotes a retired documentVersion filters, source authority and context selection
Agent claims an edit but no diff existsTool availability, execution result and done condition
Well-formed object violates access rulesApplication authorization, not just generation instructions
