01 / FIELD NOTES

Observe, choose, act, check

An agent is best understood through its interaction with an environment.

A task provides a goal and constraints. The system observes a partial view, chooses an action, gets a tool result, updates its working state and decides whether to continue. The environment includes files, services, users or a simulated world. The underlying real state is usually not fully visible; plans must be revised when observations contradict assumptions.

An LLM may choose the next action, but the runtime decides which actions can execute. A fixed workflow prescribes the route; an agent chooses parts of the route from observations. Many useful systems combine deterministic stages with a model-driven decision inside one stage. “More autonomous” is not automatically “more reliable.”

Teaching model: aₜ = policy(observation history, goal) Environment: stateₜ₊₁ → observationₜ₊₁ Runtime: validate(aₜ) before execution

02 / FIELD NOTES

Plans are hypotheses about useful next steps

Use observations to earn each extension of the plan.

For a code fix, first reproduce or inspect the claimed failure, locate the responsible behavior, change it, then verify the relevant property. A plan can identify dependencies and parallel work, but completion requires actual evidence. An action sequence that looks sensible may still be based on a wrong file, stale data or an unobserved side effect.

Multi-agent work helps when subtasks have clear inputs, independent outputs and a reconciliation procedure. It adds communication cost, duplicated context and conflicting edits. Start with one agent and deterministic checks; add delegation only when measured gains outweigh coordination cost.

03 / FIELD NOTES

Treat progress and termination as explicit states

An agent that cannot stop correctly is difficult to operate.

State / eventRequired behavior
CompletedThe output satisfies the acceptance condition with evidence
BlockedName the missing input or permission; preserve a resumable checkpoint
Tool timeoutFind out whether a side effect occurred before retrying
Repeated no progressChange the hypothesis or stop with a bounded failure report
Budget exhausted / cancelledStop new work and return the current state and remaining work

A loop bound limits damage and cost; it does not prove correctness. An idempotency key can help a tool distinguish a replay from a new request. Repeatedly sending “continue” should not duplicate a payment, message or deployment.
